2 · Fixed height — the four blocks

The component requires a height, so the experience ships as four separately embeddable blocks instead of one long frame. The page scrolls between them — no nested scrollbars, which is the thing that kills conversion on phones. Each block is stateless (the QR is amountless, so the payment block needs nothing from the calculator).

BlockURLSet heightContent range, measured 320–1440px
1 · Calculator/embed/?part=input1100px776 – 1059
2 · Result/embed/?part=result800px378 – 718
3 · Payment/embed/?part=pay1100px834 – 1058
4 · Receipt/embed/?part=receipt700px385 – 620

Each height is the measured worst case plus a margin, so nothing clips at any width from 320px to 1440px. If the component can take a different height per breakpoint, tell us and we'll hand you a two-number set instead — that removes the remaining vertical slack on desktop.

All four still work as a single page if you prefer one block: /embed/ (≈3700px — not recommended; that is the version with an internal scrollbar).

4 · What to record (one pass, five minutes)

  1. Paste Block 1 at 1100px. Confirm it renders and that no internal scrollbar appears (that is the whole point of the height table — the content must fit the box).
  2. Repeat for Blocks 2–4 at 800 / 1100 / 700px. If any block clips, tell us the width and we adjust the block, not the number.
  3. If the component sets a sandbox, add it in the bench first — then confirm the credit-card tile still leaves the iframe and lands on hollows.org/donate.
  4. Press “測試叫起 PayMe” in the bench and read the message: does the browser let the frame open the wallet app, or is the QR the only mobile path?
  5. Fill the receipt form and submit — Checks must turn email_capture to PASS.
  6. Paste a GTM container ID, load it, re-run — do the events appear in dataLayer?
  7. Press Copy test report and send it back.
